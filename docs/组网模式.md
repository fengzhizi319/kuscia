
#  1 组网模式

Kuscia 提供了灵活的组网方案，可以根据不同的业务场景和组织架构选择合适的部署模式。

| 组网模式 | 控制平面 | 节点类型 | 适用场景 |
|----------|----------|----------|----------|
| **中心化组网** | 多个 Lite 节点共享一个 Master | Lite 节点 | 大型机构内部，统一运维，资源成本低 |
| **P2P 组网** | 每个节点自带独立控制平面 | Autonomy 节点 | 小型机构、安全性要求高 |
| **混合组网** | Master + Autonomy 混合部署 | Lite + Autonomy | 复杂组织架构，部分集中部分对等 |
| **K8s 部署** | 外部 K8s 集群提供控制能力 | K8s Deployment | 已有成熟 K8s 基础设施的机构 |
| **互联互通** | 跨平台协议适配 | InterConn Adapter | 与第三方隐私计算平台协作 |

Kuscia 还支持 **中心化与 P2P 混合组网**，以及 **与第三方厂商节点互联互通**。

#  2 节点角色

| 角色 | 说明 | 运行模式 |
|------|------|----------|
| **Master** | 控制平面，负责任务调度、资源管理、路由控制 | `RunModeMaster` |
| **Lite** | 无控制平面的工作节点，依赖 Master 调度 | `RunModeLite` |
| **Autonomy** | 自带控制平面的 P2P 节点 | `RunModeAutonomy` |

#  3 基础设施部署方式

| 部署方式 | 说明 | 适用场景 |
|----------|------|----------|
| **Docker 模式** | 以 Docker 容器方式部署控制平面和节点 | 物理机/虚拟机 |
| **K8s 模式** | 将控制平面和节点以 K8s 应用方式部署 | 公有 K8s 集群 |
| **K8s 控制器模式** | 将 Kuscia Controllers、Storage、Envoy 部署在 K8s 控制平面 | 专有 K8s 集群 |

#  4 运行模式核心差异

##  4.0 模块化架构与模式白名单机制

### 4.0.1 单一二进制，多模块组合

Kuscia 采用**模块化架构设计**，所有功能被拆分为独立的模块（Module），通过**模式白名单机制**控制不同组网模式下启动哪些模块。

**核心理念：**

```
不是启动不同的软件程序，而是同一个 Kuscia 程序启动不同的模块组合
```

- **Master 模式** = 控制平面模块集合（k3s + controllers + scheduler + ...）
- **Lite 模式** = 工作节点模块集合（agent + datamesh + transport + ...）
- **Autonomy 模式** = 全部模块集合（Master + Lite 的所有模块）

### 4.0.2 模块注册与模式白名单

在 `cmd/kuscia/start/start.go` 中，每个模块注册时都声明了它支持哪些运行模式：

```go
// 模块注册示例
mm.Regist("k3s", modules.NewK3s, autonomy, master)        // 只在 Autonomy/Master 启动
mm.Regist("agent", modules.NewAgent, autonomy, lite)       // 只在 Autonomy/Lite 启动
mm.Regist("controllers", modules.NewControllersModule, autonomy, master)
mm.Regist("scheduler", modules.NewScheduler, autonomy, master)
mm.Regist("envoy", modules.NewEnvoy, autonomy, lite, master)              // 所有模式
mm.Regist("kusciaapi", modules.NewKusciaAPI, autonomy, lite, master)      // 所有模式
```

**关键代码逻辑：**

```go
// ModuleManager.Regist 的实现逻辑
func (mm *ModuleManager) Regist(name string, constructor Constructor, modes ...RunModeType) {
    // 检查当前运行模式是否在白名单中
    for _, mode := range modes {
        if mode == mm.currentRunMode {
            // 当前模式在白名单中，允许该模块被实例化
            mm.modules[name] = constructor
            return
        }
    }
    // 当前模式不在白名单中，该模块不会被启动
}
```

### 4.0.3 启动流程

当 Kuscia 启动时的执行流程：

```bash

mode: master  # 或 lite 或 autonomy
```

### 4.0.4 模块依赖关系

模块启动有严格的依赖顺序，通过 `Dependencies` 结构传递：

```go
// 示例：agent 模块依赖 envoy、k3s、kusciaapi
func NewAgent(dependencies *Dependencies) (Module, error) {
    // 确保这些依赖模块已经启动
    if dependencies.RunMode == RunModeLite {
        // Lite 模式下没有本地 k3s，使用远程 API
        dependencies.ApiserverEndpoint = dependencies.Master.Endpoint
    } else {
        // Master/Autonomy 使用本地 k3s
        dependencies.ApiserverEndpoint = dependencies.K3s.APIServer.Endpoint
    }
    
    return &Agent{
        clients: dependencies.Clients,
        // ...
    }, nil
}
```

**典型依赖链：**

```
k3s → envoy → agent → datamesh
  ↓
controllers → scheduler → reporter
```

### 4.0.5 架构优势

这种设计的优势：

✅ **代码复用**：同一套代码，不同配置，减少维护成本  
✅ **职责清晰**：每个模块负责特定功能，易于理解和调试  
✅ **灵活部署**：可以根据业务需求选择适合的组网模式  
✅ **资源优化**：Lite 节点不启动不必要的控制平面组件，节省资源  
✅ **可扩展性**：新增模块只需注册并声明支持的模式即可  

---

三种运行模式并不是简单地在配置文件中切换一个字段，而是直接决定了 Kuscia 会启动哪些内部模块、是否嵌入 K3s、KubeClient 如何初始化、以及节点在联邦中扮演的角色。下面从模块组合、职责划分和配置文件三个维度进行系统对比。

##  4.1 模块启动矩阵

Kuscia 的模块注册集中在 `cmd/kuscia/start/start.go` 中。`ModuleManager.Regist` 的第三个参数开始是可变长的模式白名单，只有当前运行模式出现在白名单中的模块才会被启动。下表汇总了主要模块与模式的对应关系。

| 模块 | Master | Lite | Autonomy | 关键职责 |
|------|--------|------|----------|----------|
| **k3s** | ✅ | ❌ | ✅ | 嵌入 K3s 作为控制平面，提供 Kubernetes API Server、etcd 数据存储 |
| **agent** | ❌ | ✅ | ✅ | Kubelet 替代，管理本地容器生命周期（创建/删除 Pod、拉取镜像等） |
| **containerd** | ❌ | ✅* | ✅* | 本地容器运行时，仅在 `EnableContainerd=true` 时启动 |
| **controllers** | ✅ | ❌ | ✅ | 运行 Kuscia 自定义控制器（Domain、Task、Job、AppImage 等 CRD 的调和逻辑） |
| **coredns** | ✅ | ✅ | ✅ | 为 K3s 集群与 Pod 提供 DNS 服务，支持服务发现 |
| **scheduler** | ✅ | ❌ | ✅ | 运行增强版 kube-scheduler，支持 Kuscia 调度策略（All-or-Nothing、资源预留等） |
| **datamesh** | ❌ | ✅ | ✅ | 提供数据访问代理与 Arrow Flight 服务，实现数据虚拟化 |
| **transport** | ❌ | ✅ | ✅ | 提供节点间安全通信通道，处理跨域数据传输 |
| **domainroute** | ✅ | ✅ | ✅ | 维护跨域路由与证书交换，管理 Domain/ClusterDomainRoute CRD |
| **interconn** | ✅ | ❌ | ✅ | 互联互通协议适配器，支持 BFIA/Kuscia-InterOp 等协议 |
| **reporter** | ✅ | ❌ | ✅ | 负责节点任务状态上报/采集，同步跨域任务状态 |
| **kusciaapi** | ✅ | ✅ | ✅ | 对外暴露 Kuscia API（HTTP/gRPC），非 Master 模式下 Initiator 默认为 DomainID |
| **envoy** | ✅ | ✅ | ✅ | 七层网关，代理跨域与域内流量，提供服务网格能力 |
| **confmanager** | ✅ | ✅ | ✅ | 配置中心，Lite 模式下复用 Master 签发的域证书 |
| **metricexporter/nodeexporter/ssexporter/diagnose** | ✅ | ✅ | ✅ | 监控、节点指标、系统状态、诊断等可观测模块 |

> *注：containerd 是否启动取决于运行时配置；若使用外部容器运行时则不会注册。*

从上表可以清晰看出：

- **Master** 只承担控制平面职责：运行 K3s、controllers、scheduler、reporter 等，负责任务调度和集群管理。
- **Lite** 只承担工作节点职责：运行 agent、datamesh、transport 等，通过 `masterEndpoint` 连接到远程 Master 的 K3s API，执行实际计算任务。
- **Autonomy** 是 Master 与 Lite 的合体：既嵌入 K3s 控制平面，又运行 agent 等数据平面模块，因此具备独立对外提供联邦协作的能力（P2P 节点）。

##  4.2 控制平面与数据平面职责划分

| 维度 | Master | Lite | Autonomy |
|------|--------|------|----------|
| **是否嵌入 K3s** | 是 | 否 | 是 |
| **K8s API 来源** | 本地 K3s | 远程 Master | 本地 K3s |
| **是否运行 Agent** | 否 | 是 | 是 |
| **是否运行 Scheduler** | 是 | 否 | 是 |
| **是否运行 Controllers** | 是 | 否 | 是 |
| **域证书来源** | 自签 CA | 由 Master 注册时签发 | 自签 CA |
| **典型部署位置** | 中心集群 | 参与方边缘节点 | 独立参与方全栈节点 |

##  4.3 配置文件结构差异

Kuscia 为三种模式定义了独立的配置结构体，位于 `cmd/kuscia/confloader/kuscia_config.go`。

### 4.3.1 CommonConfig（通用配置）

所有模式共享的基础配置：

```go
type CommonConfig struct {
    Mode          string          `yaml:"mode"`              // 运行模式：master/lite/autonomy
    DomainID      string          `yaml:"domainID"`          // 域标识，唯一标识当前节点所属的域
    DomainKeyData string          `yaml:"domainKeyData"`     // 域私钥（Base64 编码），用于 TLS 证书签名和身份认证
    LogLevel      string          `yaml:"logLevel"`          // 日志级别：DEBUG/INFO/WARN/ERROR
    Protocol      common.Protocol `yaml:"protocol,omitempty"` // 通信协议：HTTP/HTTPS/gRPC
}
```

**字段详细说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `mode` | string | 是 | 指定 Kuscia 节点的运行模式。可选值：`master`、`lite`、`autonomy`。决定启动哪些模块 |
| `domainID` | string | 是 | 域的唯一标识符，在跨域通信中作为节点身份。必须符合 DNS_LABEL 规范（小写字母、数字、连字符） |
| `domainKeyData` | string | 是 | RSA 私钥的 Base64 编码字符串，用于：<br>1. 生成域证书（TLS）<br>2. 签署 CSR 请求<br>3. UID-RSA Token 校验<br>可通过 `openssl genrsa` 生成后 Base64 编码 |
| `logLevel` | string | 否 | 日志输出级别。可选值：`DEBUG`（调试）、`INFO`（信息）、`WARN`（警告）、`ERROR`（错误）。默认 `INFO` |
| `protocol` | string | 否 | 内部组件间通信协议。可选值：`HTTP`、`HTTPS`、`gRPC`。默认 `HTTP` |

---

### 4.3.2 Master 配置（MasterKusciaConfig）

Master 节点作为控制平面，主要负责集群管理和任务调度：

```go
type MasterKusciaConfig struct {
    CommonConfig      `yaml:",inline"`           // 继承通用配置
    DatastoreEndpoint string `yaml:"datastoreEndpoint"`  // etcd/Datastore 地址
    ClusterToken      string `yaml:"clusterToken,omitempty"` // K3s 集群加入令牌
    AdvancedConfig    `yaml:",inline"`           // 高级配置
    GarbageCollection GarbageCollectionConfig `yaml:"garbageCollection,omitempty"` // 垃圾回收配置
}
```

**关键字段详细说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `datastoreEndpoint` | string | 是 | etcd 或数据存储服务的访问端点。格式：`https://etcd-host:2379`。Master 使用此地址存储 Kubernetes 对象状态（Jobs、Tasks、Domains 等 CRD 资源） |
| `clusterToken` | string | 否 | K3s 集群的加入令牌，用于 Lite/Autonomy 节点加入 Master 时的身份验证。若未设置，Master 会自动生成一个随机 token |

**AdvancedConfig（高级配置）详解：**

```go
type AdvancedConfig struct {
    KusciaAPI             *kaconfig.KusciaAPIConfig   `yaml:"kusciaAPI,omitempty"`              // KusciaAPI 服务配置
    ConfManager           *cmconfig.ConfManagerConfig `yaml:"confManager,omitempty"`            // 配置管理器配置
    DataMesh              *dmconfig.DataMeshConfig    `yaml:"dataMesh,omitempty"`               // DataMesh 数据网格配置

    Agent                 config.AgentConfig          `yaml:"agent,omitempty"`                  // Agent 配置（Autonomy 模式使用）
    Debug                 bool                        `yaml:"debug,omitempty"`                  // 是否启用调试模式
    DebugPort             int                         `yaml:"debugPort,omitempty"`              // 调试端口（pprof）
    EnableWorkloadApprove bool                        `yaml:"enableWorkloadApprove,omitempty"`  // 是否启用工作负载审批
    Logrotate             LogrotateConfig             `yaml:"logrotate,omitempty"`              // 日志轮转配置
    KusciaAPISans         []string                    `yaml:"kusciaAPISans,omitempty"`          // KusciaAPI TLS 证书的 SAN 列表
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `kusciaAPI` | object | KusciaAPI HTTP/gRPC 服务配置，包括监听端口、TLS 证书、认证方式等 |
| `confManager` | object | 配置管理器配置，负责动态加载和更新域配置、证书等 |
| `dataMesh` | object | DataMesh 配置，定义数据源管理、数据访问控制、数据虚拟化等策略 |
| `domainRoute` | object | 域路由配置，包括外部 TLS 证书、路由规则、负载均衡策略等 |
| `agent` | object | Agent 配置，仅在 Autonomy 模式下生效。包含容器运行时、资源容量、节点标签等 |
| `debug` | bool | 是否启用 Go pprof 调试接口。生产环境建议设为 `false` |

| `enableWorkloadApprove` | bool | 是否启用工作负载审批机制。启用后，跨域任务需要目标域手动批准才能执行 |
| `logrotate` | object | 日志轮转配置，控制日志文件大小、保留数量、保存天数等 |
| `kusciaAPISans` | array | KusciaAPI TLS 证书的 Subject Alternative Names 列表。支持 IP 地址和域名，如 `["127.0.0.1", "kuscia-api.example.com"]` |

**LogrotateConfig（日志轮转配置）：**

```go
type LogrotateConfig struct {
```

| 字段 | 类型 | 默认值 | 说明 |

**GarbageCollectionConfig（垃圾回收配置）：**

用于清理已完成的任务资源（Pod、Service、ConfigMap 等）：

```go
type GarbageCollectionConfig struct {
    EnableGC           bool          `yaml:"enableGC"`             // 是否启用垃圾回收
    GCInterval         time.Duration `yaml:"gcInterval"`           // 垃圾回收间隔
    CompletedJobTTL    time.Duration `yaml:"completedJobTTL"`      // 已完成 Job 的保留时间

```

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `enableGC` | bool | true | 是否启用自动垃圾回收。禁用后需手动清理资源 |
| `gcInterval` | duration | 1h | 垃圾回收的执行间隔。如 `1h`、`30m` |
| `completedJobTTL` | duration | 24h | 成功完成的 Job 及其关联资源的保留时间。超时后自动删除 |
| `failedJobTTL` | duration | 72h | 失败的 Job 及其关联资源的保留时间。通常比成功 Job 保留更久，便于排查问题 |

### 4.3.3 Lite 配置（LiteKusciaConfig）

Lite 节点作为纯工作节点，不包含控制平面组件：

```go
type LiteKusciaConfig struct {
    CommonConfig      `yaml:",inline"`                      // 继承通用配置
    LiteDeployToken   string                      `yaml:"liteDeployToken"`   // Lite 部署令牌
    MasterEndpoint    string                      `yaml:"masterEndpoint"`    // Master API 端点
    Runtime           string                      `yaml:"runtime"`           // 容器运行时类型
    Runk              RunkConfig                  `yaml:"runk"`              // Runk 容器运行时配置
    Capacity          config.CapacityCfg          `yaml:"capacity"`          // 节点资源容量
    ReservedResources config.ReservedResourcesCfg `yaml:"reservedResources"` // 预留资源
    Image             ImageConfig                 `yaml:"image"`             // 镜像拉取配置
    AdvancedConfig    `yaml:",inline"`                      // 高级配置
    GarbageCollection GarbageCollectionConfig     `yaml:"garbageCollection,omitempty"` // 垃圾回收配置
}
```

**关键字段详细说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `liteDeployToken` | string | 是 | Lite 节点注册到 Master 时的认证令牌。Master 会验证此 token 以确认 Lite 节点的合法性。类似于 Kubernetes 的 bootstrap token |
| `masterEndpoint` | string | 是 | Master 节点的 API Server 访问地址。格式：`https://master-host:6443`。Lite 通过此地址与 Master 通信，获取任务、上报状态 |
| `runtime` | string | 是 | 容器运行时类型。可选值：`k8s`（使用 Kubernetes API）、`cri`（直接使用 containerd CRI）。默认 `k8s` |
| `runk` | object | 是 | Runk 容器运行时配置，定义 Pod 的网络、DNS、日志等参数 |
| `capacity` | object | 是 | 节点资源容量配置，声明 Lite 节点可用的 CPU、内存、带宽等资源总量 |
| `reservedResources` | object | 否 | 预留资源配置，从总容量中扣除供系统使用的资源，避免资源竞争 |
| `image` | object | 否 | 镜像拉取配置，包括默认仓库、认证信息、代理设置等 |

**RunkConfig（Runk 容器运行时配置）详解：**

```go
type RunkConfig struct {
    Namespace      string   `yaml:"namespace"`        // Kubernetes Namespace
    DNSServers     []string `yaml:"dnsServers"`       // DNS 服务器列表
    KubeconfigFile string   `yaml:"kubeconfigFile"`   // Kubeconfig 文件路径
    EnableLogging  bool     `yaml:"enableLogging"`    // 是否启用日志收集
    LogDirectory   string   `yaml:"logDirectory"`     // 日志目录
    LogMaxFiles    int      `yaml:"logMaxFiles"`      // 最大日志文件数
    LogMaxSize     string   `yaml:"logMaxSize"`       // 单个日志最大大小
}
```

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|

##  5.1 模块注册差异（`cmd/kuscia/start/start.go`）

```go
mm.Regist("controllers", modules.NewControllersModule, autonomy, master)
```

`ModuleManager.Regist` 的第三个参数开始是可变长的模式白名单；如果当前运行模式不在白名单中，该模块不会被实例化。例如 Lite 节点不会启动 `k3s`、`controllers`、`scheduler`、`reporter`、`interconn`，因此进程数更少、资源占用更低。第 4.1 节还会进一步说明模块间的依赖关系（如 `envoy -> k3s`、`agent -> envoy/k3s/kusciaapi` 等）。

`BuildModuleRuntimeConfigs` 在读取 `kuscia.yaml` 后，会按模式填充 `ModuleRuntimeConfigs`。关键差异如下。

#  6 跨域组合与管理机制

Kuscia 支持多种参与方组合方式，通过声明式 API 和控制器调和机制实现统一的跨域管理。本节详细说明不同组网模式下的节点如何发现、注册、认证和通信。

##  6.1 核心概念

在深入组网细节前，需要理解以下关键概念：

| 概念 | 说明 |
|------|------|
| **Domain（域）** | 每个参与方的唯一标识，如 `alice`、`bob`，对应一个 Kubernetes Namespace |
| **Deploy Token** | 用于节点注册的临时令牌，由 Master/Autonomy 生成，一次性使用，存储在 `Domain.Status.DeployTokenStatuses` |
| **DomainRoute** | 命名空间级别的跨域路由配置，包含证书、Token、心跳等状态 |
| **ClusterDomainRoute** | 集群级别的跨域路由，自动同步到源域和目标域的 Namespace |
| **Handshake（握手）** | 双向认证过程，交换加密 Token 并建立安全通信通道 |
| **Revision Token** | 握手后生成的会话 Token，用于后续所有跨域请求的鉴权 |

##  6.2 P2P 组网（Autonomy 模式）的组合与管理

### 场景描述

多个参与方（如 Alice、Bob、Charlie）各自独立部署完整的 Autonomy 节点，彼此对等，没有中心控制平面。

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Alice Node  │◄────┤   Bob Node   │────►│ Charlie Node │
│  Autonomy    │     │  Autonomy    │     │  Autonomy    │
│  - K3s       │     │  - K3s       │     │  - K3s       │
│  - Agent     │     │  - Agent     │     │  - Agent     │
│  - CA        │     │  - CA        │     │  - CA        │
└──────────────┘     └──────────────┘     └──────────────┘
```

### 初始化阶段

每个参与方独立启动自己的 Autonomy 节点：

```bash
# Alice 节点
./kuscia.sh autonomy --domain-id=alice --runtime=runc

# Bob 节点  
./kuscia.sh autonomy --domain-id=bob --runtime=runc

# Charlie 节点
./kuscia.sh autonomy --domain-id=charlie --runtime=runc
```

**每个节点启动时：**
- ✅ 嵌入 K3s（本地 API Server + etcd）
- ✅ 运行 Controllers（Domain、Task、Job 控制器）
- ✅ 运行 Agent（管理本地容器）
- ✅ 运行 Scheduler（调度任务）
- ✅ 自签 CA 证书，生成本地域证书

此时，**各节点完全独立，互不相识**。

### 跨域注册流程（以 Alice 连接 Bob 为例）

#### 步骤 1：创建 Domain CRD

在 **Alice 的 K3s** 中手动创建 Bob 的 Domain 对象：

```yaml
# alice-node: kubectl apply -f bob-domain.yaml

kind: Domain
metadata:
  name: bob
spec:
  cert: ""  # 初始为空，等待注册后填充
  authCenter:
    tokenGenMethod: UID-RSA  # 认证方式
```

同样，**Bob 也需要创建 Alice 的 Domain 对象**。

#### 步骤 2：生成 Deploy Token

在 **Alice 节点**，Domain Controller 会自动为 `bob` Domain 生成 Deploy Token：


生成的 Token 存储在 `Domain.Status.DeployTokenStatuses` 中，状态为 `unused`。

#### 步骤 3：配置 ClusterDomainRoute

在 **Alice 节点**创建 ClusterDomainRoute：


**ClusterDomainRoute Controller** 会自动：
1. 在 `alice` namespace 下创建对应的 `DomainRoute` 对象
2. DomainRoute Module 开始尝试与 Bob 建立连接

#### 步骤 4：发起注册请求（Register）

Alice 的 **DomainRoute Module** 执行 [`RegisterDomain`](file://\\wsl.localhost\Ubuntu\home\charles\code\sfwork\kuscia\pkg\gateway\controller\register_node.go#L57-L81)：

#### 步骤 6：握手（Handshake）

注册成功后，Alice 执行 [`HandshakeToMaster`](file://\\wsl.localhost\Ubuntu\home\charles\code\sfwork\kuscia\pkg\gateway\controller\handshake.go#L742-L799)：

```go
func HandshakeToMaster(domainID string, pathPrefix string, prikey *rsa.PrivateKey, masterPubKey *rsa.PublicKey) (*RevisionToken, error) {
    // 1. 准备握手请求
    handshakeReq, sourceToken, err := prepareHandshakeReq(domainID, pathPrefix, prikey, masterPubKey)
    // - 生成随机 Token（源 Token）
    // - 用 Bob 公钥加密源 Token
    // - 计算 Alice 公钥哈希
    
    // 2. 发送握手请求到 Bob
    resp := &handshake.HandShakeResponse{}
    utils.DoHTTP(handshakeReq, resp, &utils.HTTPParam{
        Path: "/handshake",
        KusciaHost: "bob.master.svc",
    })
    
    // 3. 解密 Bob 返回的 Token（目标 Token）
    token, decryptErr := decryptToken(prikey, resp.Token.Token, tokenByteSize/2)
    
    // 4. 拼接完整 Token：sourceToken + targetToken
    token = append(sourceToken, token...)
    
    // 5. 将 Token 添加到 Envoy 集群配置
    addMasterClusters(domainID, pathPrefix, token)
    
    return &RevisionToken{
        RawToken: token,
        Revision: resp.Token.Revision,
    }
}
```

**UID-RSA Token 生成机制：**

```
Alice                          Bob
─────                          ───
1. 生成 random_A（16字节）
2. 用 Bob 公钥加密 random_A
3. 发送加密的 random_A  ──→  4. 用私钥解密得到 random_A
                               5. 生成 random_B（16字节）
                               6. 用 Alice 公钥加密 random_B
7. 接收加密的 random_B  ←──  8. 发送加密的 random_B
9. 用私钥解密得到 random_B
10. 最终 Token = random_A + random_B（32字节）
```

**握手结果：**
- Alice 获得双向认证的 Token
- Token 被注入到 Envoy 的 HTTP Header（`jwt-token`）
- 后续所有跨域请求都携带此 Token

#### 步骤 7：双向同步

上述流程是 **单向的**（Alice → Bob）。要实现双向通信，Bob 也需要执行相同流程连接 Alice：

```
Alice Node                          Bob Node
─────────                           ────────
1. 创建 Bob Domain              ←→  1. 创建 Alice Domain
2. 生成 Deploy Token for Bob    ←→  2. 生成 Deploy Token for Alice
3. 创建 ClusterDomainRoute      ←→  3. 创建 ClusterDomainRoute
4. Register to Bob              ←→  4. Register to Alice
5. Handshake with Bob           ←→  5. Handshake with Alice
```

```go
func (c *DomainRouteController) registerHandle(w http.ResponseWriter, r *http.Request) {
    // 1. 解析请求
    var req handshake.RegisterRequest
    json.NewDecoder(r.Body).Decode(&req)
    
    // 2. 解析 CSR
    certRequest := parseCertRequest(req.Csr)
    
    // 3. 验证 JWT Token
    //    - 使用 CSR 中的公钥验证 JWT 签名
    //    - 检查过期时间（5分钟）
    //    - 验证 SHA256 哈希是否匹配
    verifyJwtToken(r.Header.Get("jwt-token"), certRequest.PublicKey, &req)
    
    // 4. 验证 CSR 中的 CN 与 domain_id 一致
    verifyCSR(certRequest, req.DomainId)
    
    // 5. 提取并验证 Deploy Token
    regToken := getTokenFromCertRequest(certRequest)  // 从 CSR Extension 中提取
    index := deployTokenMatched(certRequest, domain.Status.DeployTokenStatuses)
    // 检查：
    // - Token 是否存在于 Domain.Status.DeployTokenStatuses
    // - Token 状态是否为 Unused
    
    // 6. 签发域证书（有效期 10 年）
    domainCrt := &x509.Certificate{
        SerialNumber:          big.NewInt(1),
        Subject:               certRequest.Subject,
        PublicKey:             certRequest.PublicKey,
        NotBefore:             time.Unix(req.RequestTime/int64(time.Second), ...),
        NotAfter:              time.Unix(req.RequestTime/int64(time.Second), ...).AddDate(10, 0, 0),
        ExtKeyUsage:           []x509.ExtKeyUsage{x509.ExtKeyUsageClientAuth, x509.ExtKeyUsageServerAuth},
        KeyUsage:              x509.KeyUsageDigitalSignature | x509.KeyUsageCertSign,
        BasicConstraintsValid: true,
    }
    domainCrtRaw := x509.CreateCertificate(rand.Reader, domainCrt, c.CaCert, 
                                           certRequest.PublicKey, c.CaKey)
    
    // 7. 更新 Domain 状态
    domain.Spec.Cert = base64.StdEncoding.EncodeToString(
        pem.EncodeToMemory(&pem.Block{Type: "CERTIFICATE", Bytes: domainCrtRaw}))
    domain.Status.DeployTokenStatuses[index].State = common.DeployTokenUsedState
    c.kusciaClient.UpdateStatus(domain)
    
    // 8. 返回证书和 Master 公钥
    json.NewEncoder(w).Encode(&handshake.RegisterResponse{
        Cert:         base64.StdEncoding.EncodeToString(domainCrtRaw),
        MasterPubkey: base64.StdEncoding.EncodeToString(c.prikey.PublicKey),
    })
}
```

| `master_pubkey` | string | Base64 编码的 Master 公钥（PKCS#1 格式），用于后续握手验证 |

```go
func (pc *PodsController) reconcilePod(pod *v1.Pod) error {
    // 1. 拉取镜像
    pc.containerRuntime.PullImage(pod.Spec.Containers[0].Image)
    
    // 2. 创建容器
    containerID := pc.containerRuntime.CreateContainer(pod, container)

    pod.Status.Phase = v1.PodRunning

        StartedAt: metav1.Now(),

}
```

```go
func (r *JobReporter) reconcileJob(job *kusciaapisv1alpha1.KusciaJob) {
    // 1. 查询所有关联的 KusciaTask
    tasks := r.taskLister.ListTasksByJob(job.Name)
    
    // 2. 检查是否所有任务都完成
    allCompleted := true
    for _, task := range tasks {
        if task.Status.Phase != "Succeeded" && task.Status.Phase != "Failed" {
            allCompleted = false
            break
        }
    }
    
    // 3. 更新 Job 状态
    if allCompleted {
        job.Status.Phase = "Completed"
        job.Status.CompletionTime = metav1.Now()
        r.kusciaClient.UpdateStatus(job)
    }
}
```

##### 核心接口列表

| 接口名称 | 协议 | 端口 | 方向 | 用途 |
|---------|------|------|------|------|
| `/register` | HTTPS POST | 8082 | Lite → Master | Lite 节点注册，获取域证书 |
| `/handshake` | HTTPS GET | 8082 | Lite ↔ Master | 双向握手，获取 Revision Token |
| `/api/v1alpha1/kusciaapi/*` | gRPC/HTTP | 1080 | Client → Master | 提交任务、查询状态 |
| K8s API Server | HTTPS | 6443 | Lite → Master | Pod/Task/Job 状态同步 |
| Envoy Proxy | HTTP/HTTPS | 8080 | Lite ↔ Master | 跨域数据传输代理 |

##### 关键资源对象流转

```
CreateJob Request (JSON)
    ↓
KusciaJob CR (YAML)
    ↓
KusciaTask CR × N (每方一个)
    ↓
Pod + ConfigMap + Service × N
    ↓
Container (SecretFlow Engine)
    ↓
Pod Status (Running/Succeeded/Failed)
    ↓
KusciaTask Status
    ↓
KusciaJob Status
    ↓
CreateJob Response (JSON)
```

##### 安全机制

1. **双向 TLS 认证**：Lite 和 Master 使用域证书进行 mTLS 通信
2. **JWT Token 校验**：注册时使用 JWT 防止伪造请求
3. **Deploy Token 一次性使用**：注册后立即标记为 Used
4. **Revision Token 会话管理**：握手后生成临时 Token，支持过期和轮换
5. **CSR 扩展字段验证**：Deploy Token 嵌入 CSR Extension，防止中间人攻击

##### 故障恢复机制

| 故障场景 | 恢复策略 |
|---------|----------|
| Lite 注册失败 | 指数退避重试（最多 5 次） |
| Pod 创建失败 | KusciaTask Controller 重新创建 |
| Container 崩溃 | 根据 restartPolicy 决定是否重启 |
| 网络中断 | Envoy 自动重连 + Token 刷新 |
| Master 宕机 | Lite 继续运行已调度的任务，新任务排队 |

---##  6.4 K8s 部署模式的组合与管理

### 场景描述

K8s 部署模式是指将 Kuscia 的控制平面和节点以 Kubernetes 应用（Deployment/Service）的方式部署到**外部已有的 K8s 集群**中，而不是使用嵌入式的 K3s。这种模式适合已经有成熟 K8s 运维体系的机构。

**两种子模式：**

1. **K8s 标准模式**：Kuscia Controllers、Storage、Envoy 作为独立 Pod 运行在 K8s 控制平面
2. **K8s 控制器模式**：仅部署 Kuscia CRD 控制器，复用现有 K8s 控制平面能力

```
┌──────────────────────────────────────────────┐
│         外部 K8s 集群（已有）                  │
│                                              │
│  ┌─────────────┐    ┌─────────────┐          │
│  │ Master Pod  │    │  Lite Pod   │          │
│  │ Deployment  │    │ Deployment  │          │
│  │ - kuscia    │    │ - kuscia    │          │
│  │   kernel    │    │   kernel    │          │
│  │ - envoy     │    │ - envoy     │          │
│  └──────┬──────┘    └──────┬──────┘          │
│         │                 │                  │
│         ▼                 ▼                  │
│  ┌─────────────────────────────┐             │
│  │  K8s API Server (外部)      │             │
│  │  - 提供调度能力              │             │
│  │  - 提供存储能力              │             │
│  └─────────────────────────────┘             │
└──────────────────────────────────────────────┘
```

### 与嵌入式 K3s 模式的核心差异

| 维度 | 嵌入式 K3s（Master/Autonomy/Lite） | K8s 部署模式 |
|------|-----------------------------------|-------------|
| **API Server 来源** | 内置 K3s API Server | 外部 K8s API Server |
| **数据存储** | K3s 内置 etcd/Datastore | MySQL/PostgreSQL/外部 etcd |
| **调度器** | 自研 Scheduler 模块 | 复用 K8s 原生调度器 |
| **网络插件** | 无（禁用 Flannel） | 复用 K8s CNI（Calico/Flannel等） |
| **证书管理** | 自签 CA | 可集成 K8s cert-manager |
| **资源隔离** | Namespace 级别 | Namespace + ResourceQuota |
| **运维复杂度** | 低（一键启动） | 高（需维护 K8s 集群） |

### K8s P2P 组网注册流程

K8s P2P 模式与 Docker Autonomy 模式的注册流程基本一致，区别在于部署方式：

#### 部署差异对比

| 项目 | Docker Autonomy | K8s P2P |
|------|----------------|---------|
| **进程管理** | Docker Compose | K8s Deployment |
| **服务发现** | Docker Network | K8s Service |
| **存储后端** | 本地 SQLite/文件 | MySQL/PostgreSQL |
| **网络暴露** | Host Port | Service LoadBalancer/Ingress |

#### 配置要点

每个参与方在自己的 K8s 集群部署完整的 Autonomy 节点：

```yaml
# autonomy-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:

data:
  kuscia.yaml: |
    domainID: alice
    domainKeyData: |
      ...
    runMode: autonomy  # P2P 模式
    datastoreEndpoint: "mysql://..."
    runtime: RunK
```

**跨域注册流程与 6.2 节 P2P 组网完全相同**：
1. 各方创建对方的 Domain CRD
2. 配置 ClusterDomainRoute
3. 执行 Register → Handshake 流程
4. 建立双向认证通道

### K8s 模式的优势与挑战

#### 优势

✅ **复用现有基础设施**：无需额外部署 K3s，降低运维成本  
✅ **资源调度更灵活**：利用 K8s 原生调度器，支持复杂调度策略  
✅ **高可用能力强**：可配置多副本、HPA、PodDisruptionBudget  
✅ **生态集成便利**：可对接 Prometheus、Istio、cert-manager 等  
✅ **权限细粒度控制**：RBAC、NetworkPolicy、ResourceQuota  

#### 挑战

⚠️ **部署复杂度高**：需熟悉 K8s YAML 配置和运维  
⚠️ **网络配置复杂**：跨集群通信需配置 LoadBalancer/Ingress  
⚠️ **调试难度大**：多层抽象（K8s → Kuscia → Task）增加排查难度  
⚠️ **资源开销较大**：每个节点都是完整 Pod，相比 Docker 模式占用更多资源  

### 运行时差异

#### K8s RunK 模式

隐私计算任务直接以 K8s Pod 形式运行：

```yaml
# 任务 Pod 示例
apiVersion: v1
kind: Pod
metadata:
  name: psi-task-abc123
  namespace: lite-bob
  labels:
    kuscia.io/job-id: job-xyz
    kuscia.io/task-id: task-abc
spec:
  containers:
    - name: psi-container
      image: secretflow/psi:latest
      command: ["python", "psi_task.py"]
      resources:
        limits:
          cpu: "4"
          memory: "8Gi"
```

**特点：**
- ✅ 任务直接由 K8s 调度，无需 Agent 转换
- ✅ 可利用 K8s 的资源限制、亲和性、容忍度等能力
- ⚠️ 需要 K8s 集群有足够权限创建 Pod

#### K8s RunP 模式

使用 Proot 技术在普通 Pod 内运行特权容器：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: kuscia-lite
  namespace: lite-bob
spec:
  containers:
    - name: kuscia
      image: secretflow/kuscia:latest-runp
      securityContext:
        privileged: false  # 无需特权
      volumeMounts:
        - name: proot-volume
          mountPath: /proot
```

**特点：**
- ✅ 无需特权容器，安全性更高
- ✅ 可在共享 K8s 集群中部署
- ⚠️ 性能略低于 RunK（Proot 开销）

##  6.6 互联互通模式（Interop）

### 场景描述

互联互通（InterConn）是指 Kuscia 与**第三方隐私计算平台**（如 FATE、OpenMMLab 等）进行跨域协作的能力。通过标准化的协议适配层，实现不同厂商系统之间的任务协同。

```
┌──────────────────┐              ┌──────────────────┐
│   Kuscia Node    │              │  Third-Party     │
│   (Alice)        │◄════════════►│  Platform        │
│                  │  InterConn   │  (Bob - FATE)    │
│  - Controllers   │   Protocol   │                  │
│  - InterConn     │              │  - Adapter       │
│    Adapter       │              │  - Scheduler     │
│  - Envoy         │              │  - Gateway       │
└──────────────────┘              └──────────────────┘
```

### 核心架构组件

#### InterConn 模块

[`InterConn`](file://\\wsl.localhost\Ubuntu\home\charles\code\sfwork\kuscia\cmd\kuscia\modules\interconn.go) 是 Kuscia 的互联互通协议适配器，仅在 **Master** 和 **Autonomy** 模式下启动：

```go
// cmd/kuscia/start/start.go
mm.Regist("interconn", modules.NewInterConn, autonomy, master)
```

**关键职责：**
1. **协议转换**：将 Kuscia 内部的任务描述转换为第三方平台可理解的格式
2. **任务映射**：维护 Kuscia Task 与第三方 Job 的对应关系
3. **状态同步**：监听第三方平台任务状态并回报到 Kuscia CRD
4. **数据桥接**：协调跨平台的数据访问权限和传输

#### InterConnScheduler

独立的调度服务，提供 HTTP/gRPC API 供第三方平台调用：

```go
// cmd/kuscia/modules/runtime.go
dependencies.InterConnSchedulerPort = defaultInterConnSchedulerPort  // 默认 9090
```

**API 端点：**
- `POST /api/v1/interconn/schedule`: 提交跨域任务
- `GET /api/v1/interconn/status/{job_id}`: 查询任务状态
- `POST /api/v1/interconn/cancel/{job_id}`: 取消任务

### 互联互通注册流程

#### 步骤 1：在第三方平台注册 Kuscia 节点

以 FATE 为例，需要在 FATE Flow 中配置 Kuscia 作为远程计算引擎：

```json
// fate_flow config
{
  "computing_engine": "KUSCIA",
  "kuscia_config": {
    "endpoint": "http://alice-gateway.example.com:1080",
    "domain_id": "alice",
    "auth_token": "shared_secret_token"
  }
}
```

#### 步骤 2：在 Kuscia 中配置第三方 Domain

在 **Kuscia Master/Autonomy** 中创建第三方平台的 Domain：

```yaml
apiVersion: kuscia.secretflow/v1alpha1
kind: Domain
metadata:
  name: bob-fate  # 第三方平台的标识
spec:
  cert: ""  # 初始为空
  authCenter:
    tokenGenMethod: UID-RSA
  interopConfig:
    protocol: FATE  # 或 OPENMMLAB、PRIVACYWARE 等
    adapterEndpoint: http://bob-fate-gateway.example.com:9380
```

**关键字段：**
- `interopConfig.protocol`: 第三方平台类型
- `interopConfig.adapterEndpoint`: 第三方平台的适配器地址

#### 步骤 3：配置 ClusterDomainRoute

创建从 Kuscia 到第三方平台的跨域路由：

```yaml
apiVersion: kuscia.secretflow/v1alpha1
kind: ClusterDomainRoute
metadata:
  name: alice-to-bob-fate
spec:
  source: alice
  destination: bob-fate
  endpoints:
    - host: bob-fate-gateway.example.com
      port: 9380
  tokenConfig:
    genMethod: UID-RSA
  interopConfig:
    enabled: true
    protocol: FATE
```

#### 步骤 4：执行 Register 和 Handshake

与标准 P2P 流程相同，但目标端点是第三方平台的适配器：

```bash
# Kuscia 自动执行
kubectl get clusterdomainroute alice-to-bob-fate -o yaml
```

**期望状态：**

```yaml
status:
  conditions:
    - type: Ready
      status: "True"
      reason: Success
  tokenStatus:
    sourceTokens:
      - token: "..."
        isReady: true
    destinationTokens:
      - token: "..."
        isReady: true
```

### 跨平台任务执行流程

#### 示例：Kuscia 发起 PSI 任务到 FATE

##### 1. 用户提交 KusciaJob

```yaml

  name: cross-platform-psi

          role: follower
```

##### 2. Kuscia Scheduler 调度任务

- 识别 `bob-fate` 为第三方 Domain
- 调用 InterConn Adapter 转换任务描述

##### 3. InterConn 转换任务

### 互联互通的安全考虑

#### 1. 双向认证

与标准 P2P 相同，使用 UID-RSA Token 机制确保双方身份可信。

#### 2. 数据隔离

第三方平台只能访问明确授权的 DomainData：

```yaml

  name: alice-grant-to-bob-fate
  namespace: alice

  dataID: dataset-001
  granteeDomain: bob-fate
  permissions:
    - READ  # 仅读，不可写
  expireTime: "2024-12-31T23:59:59Z"
```

#### 3. 审计日志

所有跨平台操作都记录审计日志：

```bash
kubectl logs deployment/kuscia-master -n kuscia-master | grep "interop"
```

**日志示例：**

### 互联互通的限制与挑战

#### 当前限制

⚠️ **协议兼容性**：不同厂商的协议实现可能存在差异  
⚠️ **功能对等性**：并非所有 Kuscia 功能都能在第三方平台找到对应实现  
⚠️ **性能开销**：协议转换和轮询增加延迟（通常 1-5 秒）  
⚠️ **调试复杂度**：跨系统问题排查需要双方团队协作  

#### 最佳实践

✅ **标准化优先**：优先使用行业标准协议（如 OpenFL）  
✅ **异步解耦**：采用事件驱动架构，避免强依赖第三方平台可用性  
✅ **超时重试**：配置合理的超时和重试策略  
✅ **监控告警**：对 InterConn 健康状态进行监控  

##  6.7 统一管理的关键机制

### 声明式 API

所有配置都通过 Kubernetes CRD 管理：
- `Domain`: 定义参与方
- `DomainRoute`: 定义跨域路由
- `ClusterDomainRoute`: 集群级路由（自动同步）
- `KusciaJob`: 定义联邦任务

### 控制器调和（Reconciliation）

每个模块都有 Controller 持续调和对期望状态：

```go
// ClusterDomainRoute Controller 伪代码
func (c *controller) Reconcile(cdr *ClusterDomainRoute) {
    // 1. 检查源域和目标域的 DomainRoute 是否存在
    srcDR := getDomainRoute(cdr.Spec.Source, cdr.Name)
    dstDR := getDomainRoute(cdr.Spec.Destination, cdr.Name)
    
    // 2. 如果不存在，创建
    if srcDR == nil {
        createDomainRoute(cdr.Spec.Source, cdr)
    }
    
    // 3. 同步状态
    syncStatusFromDomainroute(cdr, srcDR, dstDR)
    
    // 4. 更新条件
    if isReady(srcDR) && isReady(dstDR) {
        setCondition(cdr, Ready, True)
    } else {
        setCondition(cdr, Ready, False, "WaitingForPeer")
    }
}
```

### 证书生命周期管理

```
生成 CSR → 注册（Register） → 颁发证书 → 握手（Handshake） → 定期刷新
```

- **CSR 生成**: 包含 DomainID、公钥、Deploy Token
- **证书颁发**: Master/Autonomy 用自己的 CA 签名
- **握手**: 交换双向认证 Token
- **刷新**: 通过 HeartBeat 维持连接

### Token 认证机制

支持两种模式：

| 模式 | 说明 | 安全性 |
|------|------|--------|
| **UID** | 直接用对方 DomainID 作为 Token | 低（已废弃） |
| **UID-RSA** | 双方各生成随机 Token，拼接后用 RSA 加密 | 高 |

#  7 模式选择建议

| 场景 | 推荐模式 | 理由 |
|------|----------|------|
| 多方协作，由一方统一托管控制平面 | **Master + Lite** | Master 运行中心控制平面，各参与方部署 Lite 节点接入，运维边界清晰 |
| 单个机构独立部署，既要管理又要跑任务 | **Autonomy** | 一台节点即可完成控制与计算，减少部署组件数 |
| 已有外部 Kubernetes 集群，只想添加 Kuscia 能力 | **K8s 模式** | 不依赖 K3s，复用现有 K8s 控制平面 |
| 对资源极度敏感的边缘节点 | **Lite** | 不跑 K3s、scheduler、controllers，内存与 CPU 占用最低 |
| 多机构对等协作，无中心信任方 | **P2P（Autonomy）** | 各节点地位平等，双向认证，去中心化 |
| 复杂组织架构，部分集中部分对等 | **混合模式** | 灵活组合，兼顾集中管理与对等协作 |
| 对接第三方隐私计算平台 | **互联互通（InterConn）** | 标准化协议适配，跨厂商系统协同 |
